# Sidebar and explicit startup · 0.6.0 candidate

## Daily use / 매일 사용

After supervised installation and first pairing, double-click the packaged `scripts/start-swu.cmd` (or an installed shortcut targeting it). It invokes `swu start --browser`: wait for the configured Connector, then ask the installed ordinary Chrome to open Google home. It passes no profile switch, user-data directory, incognito flag, credentials or page-generated arguments. Existing tabs/profile are not intentionally replaced. This is an explicit launcher, not login autostart, a service or a registry/native-host installation. Node22+ must already be on PATH for the double-click entry point; the runtime child itself uses the absolute current Node executable and absolute packaged CLI path, with shell:false and hidden detached stdio.

From the intended active HTTP(S) tab, click SWU's toolbar icon. It opens Chrome's native side panel in that window directly in the user gesture and, only for that gesture, attempts connection if pairing and the Connector are ready. The UI offers **현재 페이지**, **사이트 기능**, **설정**, a persistent status, current visible reading and accessible advanced disclosure buttons. Original authoring, lifecycle, filtered reading, evidence, documents and operation controls remain available in those disclosures. Page text is untrusted data, displayed with textContent; there is no pretend chat or generated success content. Light/dark layouts adapt to narrow sidebars; actual visual/accessibility review is still required.

Chrome requires the `sidePanel` permission and a user gesture for `sidePanel.open()`; this candidate adds only that permission. The default_popup is removed; popup.html remains the exact internal sender/path for the side panel. Source: [official Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel). Startup, worker restart and tab switches never open/bind on their own. A sidebar selected from Chrome's panel menu may not grant activeTab: use the intended tab's toolbar gesture if the URL is unavailable. No all-sites grant or focus workaround is added.

## First installation / 첫 설치

1. Supervisor builds and manually loads `dist/extension`; this worker does not install or refresh a live build. Confirm extension identity and the added sidePanel permission. Existing token storage is retained when the extension identity is unchanged.
2. Initialize once with `swu init EXTENSION_ID` as documented in README. Start with `swu start` or the packaged launcher. Missing configuration returns `setup-required`; it does not fabricate credentials or silently initialize/change an account.
3. Open the side panel's Settings and locally copy the private pairing token once. Never paste the token into chat/logs. The worker never exports it as a process argument or diagnostic detail.
4. Click the toolbar on the intended web tab. Manual connection inside the panel queries only that panel's own window. Before/after-injection active/focus/window/HTTP(S) guards remain intact; opening a sidebar is not proof that those guards pass.

## Automatic boundaries and status

Automatic connection is only a response to an explicit toolbar invocation. Paused/fenced/unavailable runtime and explicit manual-disconnect state prevent it. A ready Connector with no initial browser binding can connect on that gesture; this is distinct from an explicit user disconnect. Manual disconnect is retained in extension session storage across worker restarts and requires the panel's explicit Connect action to clear. If another live binding is owned, toolbar invocation does not silently steal it; disconnect/inspect explicitly. No input, procedure or unknown receipt is retried. Automatic bridge requests carry intent:automatic and the status-observed session. Runtime.bind synchronously rejects pause, fence, pending/queued work, a changed session or any established owner before disconnect/reset; worker status checks alone are not authorization. Manual bind remains explicit recovery.

Status distinguishes pairing-needed, runtime-unavailable, target-needed, connected, paused, fenced and explicitly disconnected. Connected/current additionally requires the worker's nonempty local session/binding to match runtime ownership and the panel's current foreground window. A remote live binding or HTTP response alone cannot satisfy that check. Current toolbar errors are polled into the panel, and a successful connection clears only stale connection-error display. The panel checks its own window's current foreground eligibility before showing ready connection. This is advisory status, never input permission. Status reads are polled only while visible, with one request at a time; hidden/unloaded responses are ignored and timers stop. An already sent read-only status request may settle after hiding. There is no background monitor service.

## Connector readiness

`swu start` / `swu ensureRuntime` reuse a ready authenticated runtime. If absent and no runtime.lock is present, start `node ABSOLUTE_CLI_PATH serve` hidden/detached and wait for bounded readiness (default10seconds). Concurrent starters may each launch a contender, but the existing serve `wx` lock permits one owner; losers never remove its lock. A present nonready lock is preserved and reported for explicit diagnosis, not deleted based on a guessed PID. Readiness timeout is not proof that a child never started; inspect the existing owner before trying another start. Child output is ignored to avoid credential/log leakage. No new daemon or distributed lock is introduced.

`swu mcp` now ensures compatible Connector readiness before serving stdio, without opening Chrome. A responsive old process without bindProtocol:guarded-auto-v1 (including0.5) returns runtime-update-restart-required, with no spawn/kill/lock deletion/token change. A supervisor-owned explicit update/restart is separate. Probe timeouts are positive integer milliseconds even with a fractional performance clock. `swu start --browser` is the only new browser-launch path; browser launch happens after readiness. Windows executable candidates are fixed installed Chrome locations, invoked as an absolute executable with the sole Google-home argument and shell:false. The explicit Chrome launch uses windowsHide:false to show its normal browser window; only the runtime child uses windowsHide:true. Other platforms or missing Chrome receive a manual-open diagnostic. Runtime startup and browser opening are not performed by this implementation worker.
